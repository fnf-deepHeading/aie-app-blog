> **요약** — 지난번에 여러 AI가 하나를 기억하게 만드는 공유 메모리 계층을 붙였다. 그런데 그 기억은 **평평한 시간순 로그**였다. "이 주제의 현재 최신 결론"을 이름으로 지목할 방법이 없었다. Block의 [Buzz](https://github.com/block/buzz)에 그 문제를 정면으로 다룬 스펙(NIP-AE Agent Engrams)이 있어서, 데이터 모델과 동시성 규율만 이식했다. 암호화·서명은 의도적으로 버렸다 — 내 디스크의 로컬 SQLite 파일에는 그 겹이 막아줄 위협이 없다. 12개 태스크, 16커밋, 테스트 144개. 그리고 이 글의 절반은 **리뷰가 내가 쓴 계획의 오류를 네 번 잡아낸 이야기**다.

## 지난 칸에서 남은 문제

[여러 AI가 하나를 기억하게 만들기](/posts/shared-memory-for-many-agents)에서 사다리를 그렸다. 세션 간 → 에이전트 간 → 디바이스 간 → 팀 간으로 기억의 경계가 넓어지는 그림이었고, 두 번째 칸까지 올라갔다. 내 컴퓨터의 세 에이전트(터미널의 Claude Code, 슬랙 봇 Hermes, 자율 코딩 CLI)가 `operations.db` 한 파일을 공유 진실로 쓰게 됐다.

몇 달 쓰다 보니 다른 종류의 불편이 남았다. **기억이 전부 시간순 로그였다.**

`worklog`에 1,600여 행이 쌓였다. "언제 무엇을 명령하고 무엇을 했는지"가 자동으로 들어온다. 좋다. 그런데 "공유 메모리 계층을 어떻게 하기로 했더라"를 알고 싶으면 `decisions`를 시간순으로 훑고 `supersedes_id` 체인을 따라가야 했다. 그래서 실제로 그 테이블은 **3행에서 멈췄다.** 쓰기 비용보다 읽기 비용이 커서 아무도 안 썼다.

필요한 건 이름으로 지목되는 슬롯이었다. `mem/shared/decision/shared-memory-layer` 하나를 읽으면 현재 결론이 나오고, 갱신하면 같은 주소에 새 버전이 얹히는 구조.

## Buzz에는 그 스펙이 이미 있었다

[block/buzz](https://github.com/block/buzz)를 훑다가 `crates/buzz-core/src/engram.rs`(1,049줄)에서 멈췄다. **NIP-AE Agent Engrams** — AI 에이전트 기억 전용 스펙이고, `docs/nips/NIP-AE.md`에 21KB로 명세돼 있다.

| 요소 | Buzz의 설계 |
|---|---|
| 저장 단위 | `kind:30174` 이벤트 (파라미터화 교체 가능) |
| 주소 지정 | 슬러그(`core`, `mem/…`)를 **HMAC**한 `d`-tag → 릴레이가 내용을 몰라도 교체 가능 |
| 암호화 | NIP-44 v2, 본문 65,535바이트 상한 |
| 주입 시점 | ACP 하네스가 **세션 생성 시 core engram 주입** |
| 갱신 규칙 | `select_head` + `monotonic_created_at`, tombstone 삭제 |
| 참조 | `[[슬러그]]` 위키링크, `core`를 뿌리로 도달성 그래프 |

Buzz 전체의 에이전트 사상도 인상적이었다. README의 표현으로는 *"에이전트는 방의 구성원이지, 귀신 들린 cron job이 아니다"*이고, 실질은 **권한을 플래그가 아니라 신분으로 준다**는 것이다. 에이전트마다 자기 키페어를 갖고, 권한 스코프 체크박스가 아니라 채널 멤버십으로 범위가 정해진다. 범위를 줄이려면 스코프를 빼는 게 아니라 방에서 뺀다.

기억 쪽에서 특히 좋았던 두 가지 선택.

**소유자 투명성을 구조로 보장한다.** `K_c`가 ECDH 대화키라 대칭이다. 스펙이 명시한다 — *"키가 대칭이므로 양쪽이 모든 이벤트를 복호화한다. 소유자는 에이전트가 기억하는 모든 것을 언제나 읽을 수 있다."* 에이전트가 소유자에게 숨길 수 있는 기억이 **암호학적으로 존재하지 않는다.** 정책이 아니라 키 유도 방식에서 나오는 성질이다.

**그러나 소유자는 쓸 수 없다.** *"소유자 쓰기 권한 없음. `seckey_a`만 레코드를 저작할 수 있다."* 볼 수 있지만 고칠 수 없다. 감시와 조작을 분리한 설계다.

## 이식이 아니라 번역이었다

여기서 중요한 판단이 있었다. NIP-AE는 네 겹으로 되어 있다.

| 겹 | 내용 | 내 환경에서의 의미 |
|---|---|---|
| ① 데이터 모델 | 슬러그, core/memory, tombstone, 참조 그래프 | **즉시 유용** |
| ② 동시성 규율 | head selection, 단조 타임스탬프, 충돌 표면화 | **즉시 유용** — writer가 셋인데 순서 보장이 없었다 |
| ③ 키페어 서명 | BIP-340 Schnorr | 로컬 단독에선 의례 |
| ④ 암호화·슬러그 은닉 | NIP-44, HMAC d-tag | **위협모델이 없다** |

④의 존재 이유는 *내가 신뢰하지 않는 릴레이*에게 슬러그를 숨기는 것이다. 그런데 `operations.db`는 내 디스크의 로컬 파일이다. 숨길 상대가 없다. 그대로 옮기면 카고컬트가 된다.

그래서 **①②만 생산 경로에 넣고, ③④는 격리된 적합성 모듈로 분리**했다. 스펙 이해를 검증하는 학습 산출물로만. 생산 코드는 그 디렉터리를 import하지 않고, 테스트로 그걸 강제한다.

더 근본적인 비틀기도 하나 있었다. 스펙의 *Roles* 절이 명확하다 — *"기억은 하나의 `(pubkey_a, pubkey_o)` 쌍에 스코프된다."* 즉 **NIP-AE의 기억은 에이전트별 사적 기억**이다. 에이전트가 둘이면 기억도 둘로 갈린다.

내 시스템의 존재 이유는 정반대다. 세 컴포넌트가 **공통 진실 기준이 없다**는 게 원래 문제였다. 원문대로 옮기면 내가 해결한 문제로 되돌아간다. 그래서 전역 `core` 하나 + `mem/shared/…` 공용 + `mem/agent/<이름>/…` 개별로 스코프를 의도적으로 비틀었다.

의도적으로 버린 것과 그 이유를 스펙 문서에 **표로 명시**했다. 나중에 누군가 "이거 Buzz 릴레이에 그대로 올리면 되겠네"라고 오해하지 않도록, 생산 경로의 `event_id`가 NIP-01과 호환되지 않는다는 것도 적었다.

## 만든 것

기존 층을 대체하지 않고 위에 얹었다. `worklog` 1,600여 행은 **손대지 않았다.**

```
[append-only 원천 — 무수정]        [engram 층 — 신규]           [투영]
worklog 1,650행 ─┐
decisions        ─┼─ 큐레이션 ─▶ engrams (SQLite)  ─▶ vault .md ─▶ 의미검색
attempts         ─┘                   │                        └─▶ Obsidian 그래프 뷰
                                      ├─▶ MCP 도구 4개 (Claude Code)
                                      ├─▶ CLI 서브커맨드 (Hermes)
                                      └─▶ ★ SessionStart 훅 주입
```

★가 이 작업의 실질적 가치 지점이다. 지금까지 훅은 **기록만** 했다(`UserPromptSubmit`, `Stop`). 회상은 사람이 MCP를 호출해야 했다. `SessionStart` 훅을 붙이니 `core` + 도달 가능한 상위 N개가 새 세션마다 자동으로 컨텍스트에 들어온다. **"기록은 자동, 회상은 수동"이던 비대칭이 해소됐다.**

숫자로는 이렇다.

| 항목 | 값 |
|---|---|
| 태스크 / 커밋 | 12개 / 16개 |
| 테스트 | Python 122 + TypeScript 22 |
| 신규 도구 | **0개** — 기존 MCP·CLI·훅·승격 파이프라인에 붙였다 |
| 새 테이블 | `engrams` 1개 (멱등 마이그레이션) |
| 세션 주입량 | 1,770바이트 (profile 4,000자 상한 + 항목 10×300자) |
| NIP-AE 참조 벡터 | **4개 전량 재현** (외부 의존성 0) |

공짜로 얻은 것도 있었다. NIP-AE의 참조 문법 `[[슬러그]]`가 **Obsidian 위키링크와 문자 그대로 같다.** 그래서 vault로 승격하면 변환 없이 그래프 뷰에 참조 구조가 나타난다. 스펙의 "도달성 그래프와 orphan"이 Obsidian의 그래프 뷰와 고아 노트에 1:1 대응한다. 우연이 아니라 양쪽이 위키 전통에서 같은 걸 빌려온 결과다.

로컬이라 **스펙보다 나아진 부분**도 생겼다. NIP-AE의 listing은 릴레이가 결과 수를 제한할 수 있어 best-effort지만, 로컬 단일 DB에서는 완전 열거가 보장된다. 분산 시스템의 어려움 대부분이 릴레이 집합에서 나오고, 그게 없으면 난이도가 사라진다.

## 이 글의 진짜 내용 — 리뷰가 내 계획을 네 번 잡았다

여기까지가 "만들었다"는 이야기다. 나에게 더 값진 건 **과정이 무엇을 잡아냈는가**다.

태스크마다 구현자와 리뷰어를 따로 띄웠고, 계획은 내가 미리 썼다. 그런데 **틀린 게 계획이었던 경우가 네 번**이다.

**① BIP-340 테스트 벡터 한 글자.** 적합성 모듈의 기대 서명을 기억에서 쓰다 `DCA8`을 `DBA8`로 썼다. 구현자가 자기 코드를 의심하는 대신 공식 `bitcoin/bips` CSV를 확인하고 **테스트 리터럴만** 고쳤다. 만약 내 상수에 구현을 맞췄다면 버그 있는 암호 코드가 초록 테스트와 함께 남았을 것이다. 나머지 NIP-AE 벡터 22개는 원문에서 복사한 거라 전부 맞았다 — 손으로 쓴 하나만 틀렸다.

**② cron 스크립트의 실패 격리 방식.** 계획에 "`|| true`를 붙여라, 기존 줄들과 같은 방식"이라고 썼다. 실제 파일을 읽으니 `|| true`가 없고 `set -euo pipefail` **fail-fast**였다. 그대로 뒀다면 engram 승격이 실패할 때 이미 잘 돌던 atlas 롤업까지 멈췄다. 배치 위치도 맨 끝으로 바꿨다.

**③ 훅의 exit 0 불변식.** 계획에 "훅은 절대 세션을 깨지 않는다"고 스펙까지 써놓고, 정작 `sys.stdout.write()` 뒤에 플러시를 넣지 않았다. 플러시가 인터프리터 종료 시점, 즉 `try/except` **밖**에서 일어난다. 리뷰어가 재현했다 — 파이프 읽기 끝이 닫히면 **exit 120**. 실제 `core`가 없어 잠복 상태였고, 다음 태스크가 `core`를 쓰는 순간 무장될 예정이었다.

그리고 내가 처방한 수정도 부족했다. 플러시를 `try` 안에 넣으라고 했는데 Python이 종료 시 재플러시를 시도해서 여전히 깨졌다. 구현자가 `BrokenPipeError` 포착 + `dup2(/dev/null)`로 해결했다. **내 지시대로만 하고 끝내지 않고 검증해서 되짚어 준 게 맞았다.**

**④ `ensure_ascii` 설명이 사실 오류.** 계획에 "본문이 순수 ASCII여도 `ensure_ascii=False`가 중요하다"고 썼다. 틀렸다 — 순수 ASCII면 두 설정의 출력이 동일하다. 원문 스펙의 뜻은 "기본값에 의존하면 비ASCII가 들어오는 순간 갈라진다"였고 내가 잘못 압축했다. 그래서 참조 벡터로는 이 해저드를 **구조적으로 잡을 수 없고**, 비ASCII 단정문이 별도로 필요했다.

### 뮤테이션 테스트가 테스트의 구멍을 보여줬다

가장 배운 게 많았던 리뷰는 뮤테이션 테스트를 돌린 것이다. 코드를 일부러 망가뜨려서 테스트가 잡는지 보는 방식이다.

적합성 모듈에서 **12개 중 9개가 생존**했다. 구현은 공식 벡터 19개(BIP-340 서명 4 + 검증 15)에 전부 일치해서 정확했는데, **커밋된 테스트가 그걸 고정하지 못했다.**

- 비밀키 음수화 분기를 지워도 초록. → 키 절반에서 서명이 깨지는데, 테스트가 하필 "운 좋은 짝수 y 키"만 써서 못 잡는다.
- `lift_x`의 이차잉여 검사를 지워도 초록. → off-curve 점을 반환하는데, 테스트가 범위 가드에서 먼저 걸리는 입력만 썼다.
- `calc_padded_len`의 256 초과 분기를 지워도 초록. → 256바이트 넘는 평문이 전부 비표준 패딩이 되는데, 벡터가 51·70바이트만 쓴다.
- `base64.b64decode`에 `validate=True`가 없었다. → 이건 테스트 문제가 아니라 **실제 스펙 위반**이었다. `payload + "?iv=abc"`가 복호화에 성공한다.

여기서 스스로 실수도 했다. 뮤턴트를 직접 검증하려고 문자열 치환을 했는데, 주석과 독스트링에 같은 문자열이 먼저 나와서 코드가 아닌 **설명문을 때렸다.** 뮤턴트가 적용되지 않은 것을 "테스트가 약하다"고 잘못 읽었다. 줄 번호를 지정해 다시 하니 전부 사살됐다. 검증 방법 자체를 검증해야 한다는 걸 배웠다.

교훈을 한 줄로 하면 — **"코드가 정확하다"와 "테스트가 그걸 지켜준다"는 다른 문장이다.** 구현자 한 명이 자기 보고서에서 "세 분기 모두 지나갔다"고 썼는데 리뷰어가 뮤턴트로 확인해 보니 한 분기는 어떤 테스트도 안 지나갔다. 분기 자체는 정확했다. 주장이 근거 없었을 뿐이다.

## 앞으로 할 것

최종 전체 브랜치 리뷰는 **READY WITH FIXES**로 나왔다. 개별 태스크 리뷰가 구조적으로 볼 수 없던 것들이다.

**① `value` 생략 시 조용한 파괴.** `engram_write(slug=…, agent=…)`에서 `value`를 잊으면 tombstone이 되고, 반환값이 정상 교체와 **바이트 단위로 동일**하다. 그다음 15분 cron이 vault 노트를 삭제한다. 저장소 의미론은 맞다(`tombstone()`이 그 경로에 의존한다) — 문제는 "write"라는 이름의 액션이 선택적 파라미터로 파괴 경로를 노출한 것이다. 두 표면(MCP·CLI)에서 거부해야 한다.

**② 유효성 판정이 6개 지점에 4가지 정의.** 중복 키 body를 넣으면 Python은 슬러그를 누락, TypeScript는 유지, 대시보드는 렌더한다. 스펙에 중복 키 거부를 넣은 이유가 *"파서가 first-wins/last-wins로 갈리면 관측자마다 head가 달라진다"*였는데, 관측자 3명이 실제로 갈렸다.

근본 원인은 단일 슬러그 경로(`head()`)는 후보 16개를 훑어 다음 유효 행으로 내려가는데, 대량 경로는 슬러그당 1행만 뽑고 걸러내 **폴백이 없다**는 것이다. 결과적으로 `read()`로는 읽히는데 모든 열거 경로에서 사라지는 기억이 생긴다. 리뷰어가 더 나은 길을 제시했다 — `SELECT DISTINCT slug` + 슬러그별 `head()`로 바꾸면 ~10줄로 예측자가 하나로 통일되고 이 문제군이 한꺼번에 닫힌다.

**③ TypeScript 클라이언트가 죽은 코드.** 크로스언어 head 합의는 증명됐다(정상 상태에서 Python·TS가 같은 값·같은 `event_id` 반환). 그런데 `chacha-coder` 안에서 아무도 그 클라이언트를 호출하지 않는다. 즉 **coder는 여전히 engram을 못 읽고**, 스펙이 주장한 "세 에이전트 공용"이 실제로는 둘이다.

이건 고칠지 말지가 판단 문제다. 자율 코딩 CLI의 프롬프트에 기억을 주입하면 그 에이전트의 **행동이 바뀐다.** 계획의 해당 태스크는 "읽기 전용 패리티"까지만 범위를 잡았다. 기능 추가로 볼지 결함으로 볼지 결정이 필요하다.

지연 처리한 minor는 34건이다. 최종 리뷰가 분류해 줬다 — 반드시 고칠 것 1건(`search()`의 유효성 필터), 이미 해소된 것 3건, 나머지 30건은 테스트 위생·격리된 모듈의 견고성·문서화된 graceful degradation 트레이드오프라서 이월 가능.

### 다음 슬라이스

Buzz에서 아직 안 가져온 것 중 우선순위 1번은 **에이전트 잡 프로토콜**(`kind:43001~43006`)이다. `REQUEST → ACCEPTED → PROGRESS → RESULT`(+ `CANCEL`, `ERROR`) — 에이전트가 에이전트에게 일을 맡기는 절차가 프로토콜로 정의돼 있다. 오케스트레이터가 중앙에서 호출하는 구조가 아니라 동료 사이의 위임이다.

내 시스템에서 Hermes가 coder에게 일을 넘기는 절차는 지금 암묵적이다. 명시 프로토콜로 만들면 진행 상황과 실패 이유가 데이터가 된다. `attempts` 테이블이 0행인 이유가 아마 여기 있다 — 기록할 구조가 없어서 아무도 안 쓴 것이다. `decisions`가 3행에서 멈춘 것과 같은 패턴이다.

## 스펙을 읽고 배운 것

기술 내용과 별개로, NIP-AE 문서 자체가 스펙 쓰는 법의 교재였다.

**참조 테스트 벡터를 넣는다.** 키·논스·Schnorr aux를 고정하고 파생값과 완성된 이벤트 4개를 전부 박아 놓았다. 독립 구현이 "맞게 만들었는가"를 스스로 답할 수 있다.

**재구현 함정을 따로 절로 만든다.** *Implementation gotchas* 절에 "독립 재유도가 조용히 갈라질 가능성이 가장 높은 세 곳"을 적었다. NIP-44의 ECDH IKM은 raw `shared_x`다(libsecp256k1 기본값은 SHA-256을 씌운다), `aux = 0x00…00`은 "aux 생략"이 아니다(일부 바인딩이 XOR을 조용히 건너뛴다), event id 직렬화는 `ensure_ascii=False`다. **조용히 틀리는 방식을 예측해서 미리 막는 문서**다.

**한계를 명시한다.** *Security considerations*가 키 유출·메타데이터 누출·소유자 쓰기 권한 없음을 모두 적고, 특히 *"기억 오염 — 암호화는 기밀성을 주고, 에이전트가 무엇을 기억할지의 진실성은 주지 않는다. 승인 통제는 구현자의 문제다"*로 **책임 경계를 그었다.** 해결한 척하지 않는 태도다.

**한 줄로 정리하면** — 남의 스펙을 읽고 이식할 때 실제 작업은 "옮기기"가 아니라 **"각 겹이 어떤 문제에 대응하는지 묻고, 내 환경에 그 문제가 있는지 확인하기"**였다. 그리고 계획을 쓴 사람이 그 계획의 오류를 스스로 못 본다는 것 — 그래서 리뷰가 있다.
